VANI Fix Loop: research, decision and architecture

Start with the walkthrough below. After it: what 14 agents found, how we picked one design, what we build and with which tools, and how judges will see and hear a fix work.

The plan in one line. We grade every VANI call against the QA team's own 17-parameter rubric. We then trace each failure to its first wrong bot turn and group the failures into testable root causes. For the top causes we write small prompt or flow patches, and we prove each patch by forking the real failed call at the failure turn and replaying it with the old and the new bot. All of it is visible on one dashboard, and it can be heard through Sarvam voice.

1. The data we have

713 call recordings

Mono 8 kHz phone audio, 831 minutes in total. Median call 64 s, longest 6.4 min. 74 calls are under 10 s. Gemini 3 Flash transcribes them into Roman-script Hinglish with bot and user turns, at about $0.002 per minute.

Official QA rubric

17 parameters with exact Fatal and Non-Fatal rules (quantity, unit, specs, looping, dead air over 5 s, wrong product, ISQ, MCAT, and more). Fatal means an error that hurts the seller through the captured Buy Lead. Sep '26 baseline for Sarvam calls: 95% pass, 4% BL fatal.

What is missing

Human labels, the real VANI prompt, and the Buy Lead fields that were actually captured. We ask for all three on Day 1, and the design works without them.

An example from 3 test calls: the buyer switches from a school-bus CCTV camera to a home dome camera, and the bot then asks drone questions such as "flight time 45 minutes?". It also asks for the buyer's name 4 times after the buyer gave it.

2. The research: 14 agents, 3 lenses per stage

Each stage of the loop got 3 agents with different instructions. A · pragmatic looked for the most score per build hour. B · moonshot looked for what other teams will not have. C · skeptic was a different model family (Codex) and attacked the obvious approach. A Sarvam platform researcher and an independent Codex architect made 14 agents.

Sarvam researcher

Sarvam Voice Agents already has a simulated-caller Tests API with an AI judge, run per agent version, plus call logs and single-call analysis. It does not group failures across calls or suggest fixes. That gap is exactly PS1, so we plug into Sarvam instead of competing with it. Saaras v4 handles Hinglish and keyterms. Bulbul v3 supports 8 kHz output.

Codex architect

One local Python app built on Streamlit, SQLite and typed records. The differentiator is traceable repair: a judge can click from a recording to its rubric evidence, to the ranked cause, to the exact patch, to the paired test, without switching tools.

3. How we decided

We scored every option against the PS1 weights: agreement with humans 25%, root causes 25%, failure-rate drop 25%, speed 15%, coverage 10%. We also checked the overall weights (voice experience is 20%), whether it can be built in 2 days, and whether other teams are likely to have it.

Where the agents agreed

  • Extract first, then apply rules. Never one big LLM verdict. Five of five Audit and Architect agents chose this.
  • Find the first wrong bot turn, then group by mechanism. Do not cluster by embeddings, because Hinglish embeddings are noisy and the clusters are hard to explain.
  • A fix is not always a prompt. The name loop needs a code counter, and dead air is a latency setting.
  • Prove a fix with paired before and after runs, a held-out set, and passing calls kept as regression checks.

What the skeptics changed

  • Each verdict says how it knows: observed, spoken proxy or unavailable. That stops us claiming a BL error we cannot see.
  • The simulated buyer gets only frozen facts, never the failed call's script or the fix, so there is no answer leakage.
  • Negative controls: a sabotage bot must fail our test suite, or the suite proves nothing.
  • Any number from a reconstructed prompt is labelled "inferred baseline". Below 30 scenarios the result is "inconclusive".

What we reuse from AgentCI (ideas only, not code)

  • Noise-calibrated gate. AgentCI found that re-running an unchanged prompt at temperature 0 still flipped 2 of 16 held-out cases. A zero-tolerance gate rejects even a no-op change, so we measure the floor first.
  • Recovery criterion. A fix must restore good behaviour (lift of 0 or more) without more regressions than the noise floor.
  • Compounding immunity. Each fixed cause becomes a guard test, kept only if it fails on the bad bot and passes on the good one. Guards go into the tuning set, never the held-out set.

AgentCI is a personal project. To respect the "no pre-built solutions" rule, we rebuild these patterns during the event and credit the design in skills.md.

Why this wins. Most teams will build an LLM that grades calls plus a list of themes. Our edge is proof: QA's own rubric gives agreement with humans; first-fault cause cards make the causes credible; fork-the-call replay with controls shows a real drop in failures; and a native Sarvam agent version, Tests API and voice replay cover the voice-experience score. Guards add one more line for the judges: a bug we fix cannot come back.

AUDITstage 1
Does

Code counts repeat questions exactly. Fatal and low-confidence calls get a second opinion from a different model. When unsure, the grade is Needs review.
Uses
Gemini Flash for extraction. TypeSafe Jev for typed questions on every turn: which slot the bot is asking about, buyer frustration, a request for a human, whether a spec fits the product, and whether a quote supports a finding. Claude for the challenge pass. Python rules, Pydantic types.
Output
Pass, Fatal, Non-Fatal or Needs review per call and per parameter, each with a quote, a timestamp and an evidence basis. Plus 5 risk flags: wrong requirement, frustration, loops, low confidence, human request.
Validated by
40–60 calls hand-labelled by our non-tech teammate (kappa score), plus faults we plant in clean calls.
ISSUEstage 2
Does
For each failed call, finds the first wrong bot turn and writes a mechanism card: trigger, then behaviour, then consequence. It merges cards into a frozen cause list and keeps competing explanations visible. It also shows chains, for example a stale category leading to wrong ISQs leading to buyer irritation.
Assign
Jev Choice assigns each failure to the frozen cause list with a confidence score. Low-confidence failures go to a "new cause" queue for review.
Ranking
priority = (5 × fatal calls + 1 × non-fatal calls) × fixability. Each call counts once per cause. The score is shown and can be recomputed.
Output
A ranked cause list. Each cause has a name, a one-line description, a type (prompt, ASR, knowledge or flow), example calls, and a test that could disprove it.
FIXstage 3
Does
A router picks the right fix surface for each cause. For prompt causes it writes 2–3 minimal diffs against the baseline prompt. That is the real prompt if the organizers give it, otherwise one rebuilt from the calls and clearly labelled "inferred". Each diff carries its evidence quotes, the rubric rule it enforces, and conditions that reject it. A human approves it.
Uses
Gemini or Claude to draft and critique. The Sarvam Voice Agents MCP to commit the winning prompt as a new agent version.
Output
A unified diff, or a flow or keyterm change, with its rationale.
TESTstage 4
Does
Fork-the-call replay. It keeps the real call up to the failure turn, then lets the old bot and the new bot each continue against a simulated buyer that knows only frozen facts. Each case runs 5 times. The same audit rules and Jev turn questions re-grade every run. That is cheap, and it uses a different model from the bot under test. The test uses held-out calls, passing calls as regression checks, and a sabotage bot that must fail. First we replay the old bot against itself to measure the noise floor: how many good calls flip when nothing changes. A fix passes if target failures drop and new failures on good calls stay within that floor. A fix only has to restore good behaviour, not beat the baseline.
Reports
The failure rate before and after, with a 95% interval. A table of calls that flipped from fail to pass and from pass to fail. The time from finding the issue to testing the fix, measured by an automatic stopwatch.
Plus
The same scenarios run in the Sarvam Tests API on the old and the new agent version.
Guards
Each approved fix adds a permanent guard test. It must fail on the old bot and pass on the new one. Every later prompt change must pass all guards, so a fixed bug cannot return.

How we tell noise from a real issue

There are two separate questions. Neither number is guessed. Both are measured from our own runs.

In TEST: real regression, or wobble?

  1. Replay the old bot against itself. Take 30 good calls and run them 5 times each with nothing changed. Do it as 5 separate batches.
  2. Count the flips per batch. A flip is a good call that fails with no change, for example 0, 1, 1, 2, 1.
  3. Floor = the high end of that wobble. With 5 batches, use the maximum, 2. With 20 batches, use the 95th percentile.
  4. Judge the fix. 4 broken good calls is more than 2, so reject it. 1 is noise, so it passes.

Per call: a call that passed only 3 of 5 old runs is borderline, so its failure is noise. A call that passed 5 of 5 and now fails 4 of 5 is a real break, even under the floor. Re-measure the floor when the bot model, the judge or the call set changes.

In ISSUE: one-off, or recurring cause?

  • Every Fatal call stays Fatal. This rule only decides what counts as a cause worth fixing.
  • Minimum support: 3 calls. Fewer goes to an "isolated" list, for example one call whose audio could not be recovered.
  • Rank by the low end of a 95% interval on frequency, using the Wilson interval, which works for small counts. A cause seen in 20 calls outranks one seen in 3.
  • Severity overrides support. A cause with a Fatal effect on the seller is shown even at 1–2 calls, flagged "seen once, watch it".

For the demo: "We measured how much our bot wobbles when nothing changes. We call something a regression only when it breaks more than that."

6. Where TypeSafe Jev fits

Jev is a System One model. It does not write text. It answers narrow typed questions (Choice picks one option, Noul says yes or no with a probability, Score gives a level) quickly and cheaply. Code keeps control of the loop, and Jev adds the judgments that need language understanding. Python does the counting and the arithmetic, because Jev does not count reliably.

Jev does not do: fix writing, the simulated buyer, or the bot itself, because those need generated text. Inputs are text only, so Jev reads transcript turns, not audio. Limit: 64k tokens per request. Price: $0.042 per million input tokens (TypeSafe docs, checked 8 Oct 2026).

7. Do we build the voices and the tests? Yes, in 3 layers

Layer 1 · Text replay

This produces the headline numbers. It forks dozens of failed calls and runs each pair 5 times. It is fast, cheap and repeatable, and it is the evidence for the "failure-rate drop" score.

Layer 2 · Sarvam Tests API

The same scenarios run as Sarvam test cases against agent version N (old prompt) and N+1 (patched prompt). It is native to the platform, it has its own judge, and it gives the agent ID the judges ask for.

Layer 3 · Voice replay

For 2–3 showcase calls, a Bulbul-voiced buyer talks through 8 kHz phone audio to Saaras and the bot, and the bot answers in Bulbul. The judges hear the old bot fail and the new bot handle the same moment.

10. Risks and open questions

Top risks

  • No real prompt or BL fields. We label results "inferred baseline" and "spoken proxy", and we ask on Day 1.
  • Simulator too kind. Frozen facts, a sabotage-bot control, and a check that the old bot fails again in replay.
  • Jev on Hinglish is unproven. The docs say nothing about Hindi or code-mixed text. On Day 1 we test it on about 20 hand-labelled turns. If it falls short, Gemini answers the same questions.
  • Proxy or voice latency in the live demo. We pre-compute results, cache the audio, and label cached clips.

Ask organizers on Day 1

  • Can we get human QA labels, the VANI prompt, the ISQ lists per category, and the captured BL fields?
  • Is "one enquiry per day" a real policy?
  • How is Overall derived, and are calls under 10 s graded?
  • Can call text go to Sarvam LLMs? Can we get hackathon credits, given new accounts get only Rs 100?

Two decisions for you. Your data rule allows Anthropic, OpenAI and Gemini. (1) Sarvam is not on that list, but the hackathon requires it. Until the organizers confirm, Sarvam gets only synthetic or anonymized scenarios. (2) TypeSafe Jev is not on that list either. Until you approve it, Jev reads only synthetic replay turns, and Gemini answers the same questions on real call text. TypeSafe does not train on customer data. Zero data retention is an enterprise-only option.
