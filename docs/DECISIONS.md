| 2026-10-09 | At most 2 patch attempts per cause (`fix.MAX_ATTEMPTS`). `refix` refuses to write attempt 3 and `prove` refuses `--attempt 3` or a patch above attempt 2, both before any LLM call. Each gate runs at alpha 0.05 / 2 = 0.025 and the gate row records it. One gate look per (cause, attempt): `prove` refuses a second real run of a pair already in `runs/gates.jsonl` (a dry run is allowed), and re-gating after a code change needs the old rows archived by hand, outside the CLI. `fix` never replaces the patch of a cause that already has a patch or history, and prints "use refix". Amends the 2026-10-09 ship-gate decision (exact stratified permutation test, α 0.05) and the `refix` decision. | Each refix is another look at the same calls, so unlimited attempts inflate false ships. | 2026-10-09 | `pipeline issues` calls a cause a pattern only if it has at least 3 calls, its calls span at least 2 known product categories, and its latest gate row is not "replay did not reproduce the fault". A call whose category is `unknown` never counts as a category, so a cause with 1 known category plus unknowns is `single_category`; `other` counts as one category. Scores and order among patterns do not change. Every condition is judged on its own and the log keeps all failed ones. A gate row whose reason starts with "no improvement: lift" and whose old_fail_rate is 0 counts as not reproduced (rows from before #63). Other rows with rate 0 (unresolved trials, futility, identical replays) do not. `refix` and a real `prove` stop before any LLM call on a cause that is not ranked or pattern_unconfirmed. | A fault in one product line is a data signal, and a fault the OLD prompt does not show under replay cannot be proven fixed, so neither should take a fix slot. | 2026-10-09 | `pipeline golden check --version vN [--dry-run]` applies every patch whose latest gate row (its cause and attempt) says ship to the clean prompt together, and replays each golden call once under OLD and once under NEW (seed 0). | 2026-10-10 | Fix/hold-out split and a reproduction screen, both behind flags (`--holdout` on fix, refix and prove, `--screen` on prove); with no flag nothing changes. `split_half(call_id)` is the parity of the first byte of sha256(call_id): even is fix, odd is hold-out. With `--holdout`, fix and refix take evidence only from fix-half members (refix also sends no failing replay lines, which are hold-out replays) and prove picks targets only from hold-out members; the guards still avoid every failing call. With `--screen`, prove walks the seeded candidate order, replays OLD on seeds 0, 1 and 2, audits each and keeps a call when `gate.failed` holds on at least 2 of 3, until n are kept. The gate then runs on seeds 3..3+K-1 (`seed_base`; guard seeds shift too, trials keep seeds relative to the base). Screen replays go to replays.jsonl with `stage: "screen"` and count in the run cost.
